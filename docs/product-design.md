# Inkwell（墨匣）产品设计与取舍

本文说明 Inkwell（墨匣）的核心产品原则、关键设计为什么这样做，以及功能与体验边界的明确取舍。

## 1. 核心产品原则

Inkwell 面向单机个人长短篇小说创作，追求可控、透明、低噪音的写作体验，遵循四条核心原则：

- **作者掌握最终决策**：AI 协助讨论、起草、改写与核查，但正文与核心设定的正式落库必须经由作者审阅确认。
- **作品内容层与控制面分离**：日常主界面只服务于写作、资料整理与对话协作；模型配置、提示词、写作规则、排版偏好与数据备份统一收口到左下角设置入口，不干扰写作视线。
- **用清晰的模式代替复杂编排**：以少而明确的写作模式约束 AI 行为与工具边界，拒绝把通用软件工程 Agent 的重型概念硬搬进小说创作。
- **先精简，按实证演进**：覆盖真实写作刚需，在简单方案尚未遇到实证瓶颈前，不提前引入重型基础设施。

## 2. 关键设计取舍

### 为什么用「待审变更」而不是让 AI 直接改稿

长篇写作中，哪怕一个词的情绪偏差或一段对话的口吻变化，都可能破坏前后章节的连贯性。让 AI 直接写库会迫使作者不断“事后找不同”，不仅心理负担重，也容易在来回修改中丢失原本构思好的段落。

Inkwell 将 AI 对章节或设定的全部改动收口到**待审变更（Pending Changes）**：

- 每条建议都以**词/句级行内高亮 Diff** 直观呈现删改之处，作者可以在待审区逐项或一键批量应用/拒绝。
- 待审项记录提出建议时的文本基线；如果等待确认期间作者已经手动改写了该章节，应用时不会覆盖新正文，而是提示基线冲突并保留待审项由作者决定如何合并。

### 为什么用「写作模式」而不是多角色 Subagent 编排

小说创作高度依赖连续语境、人物潜台词、节奏把控与跨章节伏笔。如果把写作拆成“策划 Agent”“写手 Agent”“润色 Agent”彼此隔离对话，上下文在传递过程中极易失真，还会拉长等待时间并制造大量不可控的中间指令。

因此，Inkwell 采用单主循环 + 三种直白模式，**将工具边界直接绑定在模式上**：

- **讨论（Discuss）**：只读章节正文，专注于灵感碰撞、大纲推演与角色动机梳理；可对设定提出待审建议，并可在信息不足时向作者发起结构化提问。
- **写作（Write）**：可读取作品上下文并针对正文或设定提交待审修改建议，围绕当前场景或整章推进落稿。
- **审阅（Review）**：全只读核查模式，用于检查时间线矛盾、人物行为合理性、伏笔回收与设定一致性。

每个模式只对应**一份清晰可编辑的纯 Markdown 系统提示词**（支持随时一键恢复默认），不做多层技能包拼接、版本树或宏编译器。像会话自动命名、长对话压缩这类辅助工作，则作为独立的轻量后台单次调用完成，不制造多智能体调度复杂度。

### 为什么设计单向不可逆的「公开 / 仅全局」知识边界

许多作品同时存在两套信息：一套是随剧情推进已经公开或可自由参考的常规设定，另一套是作者自己留作底牌的隐藏伏笔、幕后真相或终局大纲。如果所有资料都无差别喂给 AI，AI 很容易在普通日常章节对话里“剧透”，或者在续写时无意识暴露主角尚未知晓的秘密。

Inkwell 对设定资料区建立了一套克制且可预期的隔离规则：

- **列表行内一键切换**：人物、背景设定、提纲、笔记四类资料均可在目录列表行内直接切换 `公开 ↔ 仅全局`，无需跳进二级弹窗修改。
- **默认最小暴露**：新建或日常对话默认处于「仅公开资料」状态，不会检索或读取标记为 `仅全局` 的条目。
- **单向升级、不可退回**：当需要和 AI 讨论隐藏主线时，点击输入框底部的「仅公开」胶囊即可一键切换为「全局 🔒」。一旦同一会话内已读取过隐藏内容，后续上下文与模型记忆便已包含这些信息，因此同会话禁止退回「仅公开」，防止产生虚假的安全感。

### 为什么坚持纯文本 Markdown + 渲染切换，而非重型富文本编辑器

富文本编辑器虽然所见即所得，但往往带来隐蔽的 DOM/JSON 序列化差异、粘贴格式污染，以及与大模型纯文本 Diff 对比时的映射脆弱性。

Inkwell 选择以**纯文本 Markdown 作为唯一正文存储格式**，并在此基础上补足日常排版与阅读舒适度：

- **双态自由切换**：按 `Ctrl+E` 或点击工具栏图标即可在源码与排版预览间切换，阅读态下双击正文任意位置即可立即回到源码编辑。
- **高频快捷键与纸面观感**：提供 `Ctrl+B`（加粗）、`Ctrl+I`（斜体）、`Ctrl+U`（下划线）快捷键，在保持无边框纸面留白的同时减少手敲星号的繁琐。
- **明确保存与草稿防丢**：按 `Ctrl+S` 或点击保存才正式写库并留存修订历史，避免每次按键都污染版本记录；同时停笔 500ms 后的未保存内容会暂存到浏览器 `localStorage`，切章保护与断电恢复兼得。

### 为什么使用 SQLite FTS5 全文检索而非默认引入向量库

在单机个人创作场景下，一部长篇小说的全部文本与设定通常只有几万到几百万字。对于作者和 AI 来说，精准查找某个专有名词、某句台词或某个时间点出现的事件，SQLite 内置的 FTS5 全文检索已经足够快且结果完全透明可预期，无需额外维护向量数据库和本地嵌入模型权重。在 FTS5 被实证遇到检索瓶颈前，保持零额外检索依赖是最稳妥的选择。

## 3. 工作区与设置中心边界

### 作品内容工作区

| 模块 | 核心职责 |
| --- | --- |
| 书架与作品管理 | 展示作品封面、书名、`X 字 · Y 章` 进度与更新日期；卡片提供导出、编辑、删除动作；顶部提供「新建作品」与「导入作品」 |
| 写作工作区（卷/章） | 分卷与章节组织（支持分卷名称、一句话副标题、折叠与拖拽排序）、可调宽目录侧栏、跨分类多文档标签页、修订历史对比与回溯 |
| 分类独立资料区 | 左轨按「角色 / 背景设定 / 提纲 / 笔记」独立分栏，支持单层文件夹与一句话副标题、行内 `公开 ↔ 仅全局` 切换、一键直建（容器外置顶、容器内追加末尾） |
| 回收站与全书搜索 | `Ctrl+K` 全书快速检索正文与设定；软删除的章节和设定进入回收站，支持随时还原或彻底清空 |
| AI 协作与待审区 | 全宽「讨论」视图与正文右侧伴随面板共享会话；支持思考强度切换、时间轴折叠思考与工具摘要、`@` 引用、悬浮复制/回滚/Fork、长会话上下文压缩，以及词/句级行内 Diff 待审区 |

### 统一设置中心（左下角控制面）

设置弹窗采用左目录、右详情的定高双栏布局，收口全部配置与服务控制，共包含六个正交板块：

- **提供商**：管理 API 连接地址、鉴权凭据与可见性，支持更新或清除已保存密钥而不回显明文。
- **模型**：发现并导入可用模型，配置提供商默认协议与单模型协议覆盖，指定默认主写作模型与后台轻量模型。
- **写作规则**：管理自动注入系统上下文的「全局规则」与针对当前作品的「单书规则」，均为纯 Markdown 自由编写，零内置套路模板。
- **写作模式**：编辑「讨论 / 写作 / 审阅」三种模式的系统提示词与默认行为边界，支持随时恢复默认。
- **编辑与阅读**：独立调节编辑器与预览区的字体、字号、行高与最大阅读宽度，修改后即时预览生效。
- **数据与服务**：查看本机服务监听地址、端口、运行状态与数据目录；触发作品导出，或创建、下载与清理完整本地 ZIP 备份（含 SQLite 数据库与附件）。

## 4. 明确不做（Non-Goals）

为保持产品简洁与架构可控，以下能力明确排除在设计之外：

- **多角色 Subagent 委派与编排**：不将小说创作拆分为多 Agent 团队协作或后台自主多轮接力管线。
- **多层技能包与工程化 PromptChain**：不引入内置技能市场、嵌套参考文档、分段宏编译器或复杂斜杠命令系统。
- **默认向量数据库与本地嵌入索引**：不预置重型本地嵌入模型或向量存储。
- **非个人本地创作能力**：不做多租户账号与远程登录鉴权、内网穿透、移动端打包、本地语音转写、重型办公文档全格式解析库，以及任何第三方统计遥测。
